> ### 🚨 TOOLING WARNING — READ THIS FIRST
> **The six persona MCP Salesforce connections are pinned to an older API version that does not expose Automotive Cloud / Industries objects.** Through those connections, `Vehicle`, `VehicleDefinition`, `Appraisal` and `AppraisalItem` all report as non-existent — `describe_object` returns "The requested resource does not exist", REST returns `sObject type 'Appraisal' is not supported`, anonymous Apex fails to compile with `Invalid type: Schema.Vehicle`, and `Schema.getGlobalDescribe()` returns 1229 objects with zero matches. **All of that is a tooling artifact. The objects are real.** The `sf` CLI (org alias `AlFardan`, **API version 68.0**) sees every one of them with live data in it.
>
> **This also fully explains the previously-unsolved "ghost field" phenomenon.** The four fields that were invisible to schema tools — `AF_TestDrive__c.AF_Vehicle__c`, `AF_TestDrive__c.AF_VehicleDefinition__c`, `Opportunity.AF_VehicleModel__c`, `Opportunity.AF_SelectedVehicle__c` — are *precisely and only* the four lookups **to** those hidden objects, so they disappeared from describe along with their targets. `AF_LeadConversionService` writes to them successfully because it compiles at its own newer API version. The mystery is closed; treat it as a solved tooling issue, not an org defect.
>
> **Method:** use the **`sf` CLI** for all schema work, metadata retrieval and any query touching `Vehicle` / `VehicleDefinition` / `Appraisal` / `AppraisalItem`. Use the **persona MCP connections** for persona-scoped DML and permission testing on everything else (they remain the only way to test as a named persona). Retrieve metadata before reasoning about validation rules, record types or flows — the MCP layer does not surface them at all.

## ALF-RS-04 — Trade-In Request and Appraisal Visibility

**User Story:** As a sales user, I should initiate trade-in requests so that the customer's current vehicle can be valued and reflected in the retail deal.
**Related Personas:** Sales Representative, Used Car Team, System
**Requirement Overview (verbatim, recovered from PDF):** *"Trade-In requests are recorded individually on the system **without the need of an Opportunity to be present**. If the trade-in request is done within opportunity stages, then the valued price appears as a negative line item on the quote reducing the final price."*

**FR1 (recovered):** The system should allow a Sales Representative to initiate a trade-in request from within the opportunity, running in parallel with the sales process **without blocking progression (up till quote stage)**.
**FR2 (recovered):** The system should require trade-in information from the Sales Representative upon creation of the request to include **Make, Model, Year, VIN, Plate Number, Mileage, Inspection Done?, Inspection Notes, Expected Trade-In Value and Source**.

> 🔑 **Two consequences of the recovery, both material:**
> 1. **The Requirement Overview mandates a standalone trade-in path** — a request must be recordable with **no Opportunity at all**. Nothing in the SD's HLD 07 design addresses this (it models trade-in purely as an "opportunity side process from Explore onward"), and it was invisible while the `.md` was the source. Covered by the new **RS-04-TC-029**.
> 2. **FR2's ten mandatory fields map almost exactly onto the live `AppraisalItem` schema** — Make=`MakeName`, Model=`ModelName`, Year=`ModelYear`, VIN=`IdentificationNumber`, Plate Number=`LicensePlateNumber`, Inspection Done?=`AF_InspectionDone__c`, Inspection Notes=`AF_InspectionNotes__c`, Expected Trade-In Value=`CustomerAskingValue`, Source=`AF_Source__c`. That 9-of-10 correspondence shows the build was done directly against FR2 — which makes the tenth, **Mileage, a high-confidence genuine gap** rather than a naming guess. See RS-04-TC-005.
