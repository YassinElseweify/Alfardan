## ALF-RS-06 — Quotation Generation in Multiple Modes

**User Story:** As a sales user, I should generate quotations in different modes so that the deal can proceed with or without an immediate VIN depending on the scenario.
**Related Personas:** Sales Representative, System

**BRD §10.6, p.43 — Requirement Overview (verbatim):** *"The system supports two quotation types: Customer Quotation and Bank Quotation, both generated from Salesforce. VIN inclusion on both types is conditional on vehicle stock status -- VIN is populated when the vehicle is in stock, and suppressed on both types when the vehicle is non-stock, in transit, or on order. Quotations include accessories, packages, trade-in deductions, and present the deal for customer review before payment."*

- **FR1** (p.43): two quotation types, same document structure, available based on customer/deal requirements
- **FR2** (p.43): conditional VIN by stock status + *"The Sales Representative may reissue the quotation with the VIN once the vehicle arrives in stock."*
- **FR3** (p.43): additional line items for accessories, packages, tint, **upsell**
- **FR4** (p.43): approved trade-in values as a negative line item / deduction
- **FR5** (p.43): present the quotation to the customer for review before proceeding to payment
- **AC1** (p.43): VIN-based quotation → *"the system validates that a VIN is linked before saving"*
- **AC2** (p.43): early-stage deal, no VIN → non-VIN quotation saves without requiring a VIN
- **AC3** (p.44): approved trade-in exists → deduction appears as a line item **reducing the total deal value**
- **Assumption 1** (p.44): final quotation types, line item structure, and output format TBC during design
- **Assumption 9** (p.44): brands subject to **per-VIN pricing** vs variant-level pricing TBC with finance/IT; per-VIN price sync mapping from Keyloop TBC

## ALF-RS-07 — Discount Approval Workflow

**User Story:** As a system, I should route discount requests through an approval matrix so that commercial governance is enforced consistently.
**Related Personas:** Sales Representative, Sales Manager / Showroom Manager, Executive Approver, System

**BRD §10.7, p.44 — Requirement Overview (verbatim):** *"Discounts support numeric value and percentage entry. Any discount applied triggers the appropriate approval path based on the delegation-of-authority matrix, potentially escalating to CEO level. Bulk approval actions are supported for executive reviewers."*

- **FR1** (p.44): *"discount entry as a numeric value only. The system should automatically calculate and display the corresponding discount percentage as a read-only derived field"*
- **FR2** (p.44): approval workflow triggered whenever a rep applies a discount, routed per the DoA matrix
- **FR3** (p.44): multi-level escalation including senior leadership and CEO-level approval above defined thresholds
- **FR4** (p.44): approval inbox/view supporting **bulk review and mass approval**
- **AC1** (p.45): discount saved → approval request automatically routed to the correct approver per the DoA matrix
- **AC2** (p.45): discount exceeding the senior leadership threshold → escalates to the defined executive approver
- **AC3** (p.45): executive approver with multiple pending requests → all visible, **bulk approval actions available**
- **Assumption 1** (p.45): final discount matrix and DoA thresholds to be supplied by the business before configuration

> ⚠ **Requirement conflict to raise with the BA regardless of test outcome.** The Requirement Overview (p.44) says *"Discounts support numeric value **and percentage** entry"*, while FR1 on the same page says *"discount entry as a numeric value **only**"* with percentage as a **read-only derived field**. These are mutually exclusive. The build implements FR1 (`AF_DiscountPercent__c` is a formula field). RS-07-TC-004 exists to document this precisely.
